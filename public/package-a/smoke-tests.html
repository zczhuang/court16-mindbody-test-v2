Part 2 · The 10 smoke-test scenarios (in order)

Every scenario uses a unique correlation ID so artifacts are traceable. After each test passes, capture the correlation ID + Deal/Contact IDs for the post-run cleanup. If any test fails, stop the run — debug before continuing.

All tests run against court16-mindbody-test.vercel.app with Ridge Hill as the chosen location.

1

Read-only calendar pull (no writes)

Cedarwind

Action: hit GET /api/mindbody/calendar?locationId=ridgehill&startDate=...&endDate=...

curl "https://court16-mindbody-test.vercel.app/api/mindbody/calendar?locationId=ridgehill&startDate=2026-05-18&endDate=2026-05-25"
Expect
  • HTTP 200
  • Response siteId is 5748154 (NOT -99)
  • classes[] contains recognizable Court 16 programs (Little Freshman, Freshman, etc.) — NOT sandbox "Fitville" / "Work out fo the day" data
2

Kids trial happy path · submission → Deal in HubSpot

Cedarwind

Action: via the UI, submit a kids trial form for a fictional kid (age 6) at Ridge Hill, picking a class ~7 days out.

Expect
  • Confirmation screen shows a correlation ID
  • HubSpot Contact appears with all 13 court16_* properties populated
  • HubSpot Deal appears in KIDS TRIALS (RIDGE HILL) pipeline at "Requested Trial" stage
  • Deal's class_date property matches the picked slot's exact start datetime
  • Deal's court16_correlation_id matches the Contact's correlation ID
  • MindBody admin (Ridge Hill site) shows a new client created with the test email
3

Staff confirm flow · Deal advances to Scheduled Trial

Cedarwind

Action: From the Contact created in test 2, copy the Court 16 staff confirm URL property → open it in a browser. Then click the same URL a second time.

Expect
  • First click: "Confirmed" HTML page · Deal stage flips to Scheduled Trial · Contact court16_booking_status flips to confirmed · MindBody admin shows the child enrolled in the actual class
  • Second click: HTTP 410 "This booking is already confirmed" (idempotency check)
4

Adult intro flow · Deal in correct pipeline with amount

Cedarwind

Action: via the UI, submit an adult intro form for Tennis Intro Special ($75) at Ridge Hill. After redirect to MindBody cart, close the cart tab (don't actually purchase).

Expect
  • Deal appears in KIDS TRIALS (BK) pipeline (Brooklyn is the "default" — verify per-location mapping in config/hubspot-deals.ts — or whichever pipeline is mapped to ridgehill for adult intros)
  • Deal name: "Adult intro · Tennis Intro Special · NY - Ridge Hill, Yonkers"
  • Deal amount: $75
  • Deal class_date populated
  • Cart URL targets Ridge Hill's MindBody (studioid=5748154)
5

Deny flow · Deal annotated, Contact failed

Cedarwind

Action: Submit a fresh kids trial. Copy the Contact's Court 16 staff deny URL, open it → pick "Wrong age band" radio → submit.

Expect
  • HTML response: "Denied. Parent will be notified ..."
  • Deal: denial_reason = "wrong_age_band" set, denial_note empty
  • Contact: court16_booking_status = failed, court16_failure_reason = "Denied: Wrong age band"
6

Reassign flow · Contact flips to manual_review

Cedarwind

Action: Submit a fresh kids trial. Open the Contact's Court 16 staff reassign URL.

Expect
  • HTML response: "Flagged for manual review. Reassign the class in MindBody, then visit the admin retry URL."
  • Contact: court16_booking_status = manual_review
  • Deal stage: UNCHANGED (per design — Deal stays at Requested Trial; staff re-confirm of new class advances it)
7

Duplicate email softwall

Cedarwind

Action: Submit the same kids trial twice in a row with identical parent email.

Expect
  • 1st submission: returns {status: "pending_staff"}
  • 2nd submission: returns {status: "duplicate_email_softwall"} · trace shows getClientsByEmail matched > 0 · no new MindBody client created
8

Age-validation rejection

Cedarwind

Action: Submit a kids trial with child age = 12 against a class named "Little Freshman ..." (which is age 3–6).

Expect
  • HTTP 400
  • Response body: {"errors": ["child age 12 is outside eligible range 3–6 for Little Freshman classes"]}
  • Zero writes — no MindBody client created, no HubSpot Contact/Deal created
9

Workflow firing (after Ibtissam enables them)

Ibtissam (verify) · Cedarwind (trigger)

Action: Submit a fresh kids trial. Wait 1h (or use HubSpot's workflow Test enrollment to skip the delay). Then run test 3 (staff confirm).

Expect
  • ~1h after submission: WF2 (Password setup) fires · password-setup email queues to the test inbox
  • Immediately after staff confirm: WF1 (Trial confirmation) fires · confirmation email queues
  • For WF3 (24h reminder): book a class ~25h out · check workflow "Performance" tab shows enrollment with a scheduled send time at class_date - 24h
  • For WF4 (Denial): run test 5 then watch the workflow fire and the denial email queue
10

Failure trace integrity

Cedarwind

Action: Submit a booking with a deliberately invalid classScheduleId (e.g. 999999999).

Expect
  • Response includes a trace[] array where one step is status: "error" with a useful message attached
  • Correlation ID intact across the entire trace
  • If the booking lands as manual_review: a Contact + Deal still appear in HubSpot (graceful degradation working) tagged with the failure reason

Part 3 · Acceptance criteria before flipping MINDBODY_WRITE_MODE=live

All five must hold

  1. ≥ 5 successful end-to-end bookings create real Ridge Hill MindBody enrollments (verifiable in the RH admin queue)
  2. 0 duplicate Contacts on email match across the test run
  3. 0 unexpected 502s in any trace response
  4. Every failure (intentional or not) is traceable from a correlation ID in the app log → HubSpot Contact → MindBody admin within 60 seconds
  5. All 4 workflows fire as expected — emails land in the test inbox at the right time, content renders without raw {{ }} tokens visible

Then, in this order:

  1. Flip MINDBODY_WRITE_MODE=live on Vercel
  2. Cleanup the test artifacts (use the 2-factor filter: court16_correlation_id HAS_PROPERTY + name pattern contains "test/smoke")
  3. Point trial.court16.com DNS at the Vercel deploy
  4. Soft-launch — send the trial URL to a small group of real parents (~20) for the first week
  5. Monitor for the 10 business days documented in Package C

Test cleanup playbook

After the smoke run, archive each test artifact safely. Use the 2-factor filter below — never archive by date + pipeline alone (one of those accidentally caught 2 real customer Deals during build).

# Safe cleanup: only catches Cedarwind-tagged artifacts (court16_correlation_id is set)
# + name matches test pattern. Never touches real customer Deals.

# Find Deals
curl -s -X POST "https://api.hubapi.com/crm/v3/objects/deals/search" \
  -H "Authorization: Bearer $HUBSPOT_ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "filterGroups":[{
      "filters":[
        {"propertyName":"court16_correlation_id","operator":"HAS_PROPERTY"},
        {"propertyName":"dealname","operator":"CONTAINS_TOKEN","value":"smoke"}
      ]
    }],
    "limit":50,
    "properties":["dealname","court16_correlation_id"]
  }'

# Then for each id: DELETE /crm/v3/objects/deals/{id}
# HubSpot DELETE is soft-archive — recoverable for 30 days via batch/restore
