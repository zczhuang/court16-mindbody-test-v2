Deny action — alongside Confirm and Reassign

Current behavior: a signed POST-based staff action records the denial state and reason before enrollment in the normal flow. It does not promise removal of an existing Mindbody visit.

What
Add a Deny action alongside Confirm / Reassign, store a reason, move the workflow state, and support reason-specific parent copy. Normal denial happens before enrollment.
Why
Today unacceptable requests get silently ignored. Deny closes the loop politely, gives the parent useful context, and produces denial-reason data for pipeline reporting.
Who
Stuart builds the route + reason picker. Ibtissam owns the reason-specific email copy (spec 08) and the HubSpot workflow that branches on reason.
Status
Route + signed action built · confirmed bookings are rejected with 410 and require Mindbody-admin cancellation

What's defined (per the SOW)

  • A third signed URL (alongside action: "confirm" and action: "reassign") with action: "deny", the same HMAC scheme, and the configurable token lifetime (72-hour default).
  • Clicking Deny opens a tiny HTML page — not an auto-apply — so staff can select a reason rather than clicking-and-regretting.
  • On submit, the Deal stage is left unchanged and the route writes Deal properties denial_reason and optional denial_note. The Contact moves to failed with a human-readable court16_failure_reason.
  • The normal path denies before a Mindbody enrollment exists. If the Contact is already confirmed, Deny returns HTTP 410 and directs staff to cancel in Mindbody admin instead.
  • The configured HubSpot workflow may branch on court16_failure_reason; its reason-to-email mapping and activation are reviewed separately.
  • The signed token is verified, and the route logs the correlation ID and chosen reason without logging the token itself.

Decide at kickoff

Ibtissam has domain context on what denial reasons actually come up in Court 16's operations. Cedarwind brings no firm proposals here — the picklist is her call.

The reason picklist

The route's concrete values map to the Deal's denial_reason property and the Contact's human-readable court16_failure_reason. Questions to resolve:

  • How many options? (Fewer is easier on staff; more is better for reporting.)
  • Is an "Other" + free-text staff-internal note needed for edge cases?
  • Which reasons need a reason-specific email vs. share a generic denial template? (Affects spec 08's email count.)

Existing-enrollment cancellation is a separate future change

MindBody's Public API v6 has /class/removeclientsfromclasses and /class/removefromwaitlist depending on whether a wait-list entry or a regular enrollment exists. Neither path is wired into the current Deny handler. A confirmed booking cannot be denied through this route; staff receives HTTP 410 and must use the approved Mindbody-admin cancellation process.

Token strategy

Two equivalent paths:

  1. Each Contact carries three signed URLs: court16_staff_confirm_url, court16_staff_reassign_url, court16_staff_deny_url.
  2. Each Contact carries one token; the staff-facing HTML pages branch on action at click time.

Option 1 matches the existing pattern (spec 01 already lists the two current URLs as Contact properties). Staying with that is the default; confirm at kickoff.
