The system is further along than any single document says, and closer to zero than the headline numbers suggest. All seven Mindbody sites were authorized on 20 July. All seven had verified trial calendars by 5 August. The booking product, a Deal-based safety ledger, double-write protection and a nineteen-script test harness are all built and deployed.

Read this first

Two things that change how you read everything else

The write-mode flag is not a safety switch.

Earlier documents — including the archived April status file — described MINDBODY_WRITE_MODE=test as a global kill switch that made every write harmless. It is not. Consumer-mode AddClient and AddClientToClass reject Mindbody’s Test parameter on real sites, so those calls persist regardless of the flag. There is no supported API delete path.

The current code replaced that assumption with two real gates: a default-off public release gate requiring per-club acceptance evidence, and a server-only write gate with an explicit Site-ID allowlist. All of them are presently false or empty. If anyone still believes the old flag protects production data, correct that belief before they touch a real site.

The default branch is six weeks stale.

main last moved on 10 July. The real state of the system — 52 commits, 158 files, roughly 22,000 added lines — lives on agent/family-account-handoff, last updated 7 August. Anyone who clones this repo and reads main gets a materially wrong picture of what exists and what is safe.

This is a genuine operational risk, not housekeeping. It is priority 5 below.

Two corrections

Things that aren’t what they sound like

There is no mobile app.

Nothing native exists — no React Native, Expo or Capacitor anywhere in the eight repositories. Every surface is responsive web. Real mobile engineering did happen, but there is no App Store deliverable and none was scoped. If a native app is wanted, that is a new conversation.

The marketing spend audit doesn’t exist yet — and that’s the finding.

Three capability audits were done: a live tag audit of court16.com on 18 June, a probe of what HubSpot’s API returns on the current tier, and a map of the Mindbody revenue endpoints. What none could produce is an audit of spend, for a simple reason: ad spend is not connected to any system Court 16 owns. It lives inside Meta and Google and reaches nothing else. Spend in the campaign console is a number somebody types in.

So marketing investment is currently unauditable, not un-audited. You can see who opened an email; you cannot see whether a campaign produced one member or one dollar. The good news is that the hardest prerequisite quietly cleared in July — all seven sites are now API-readable, so the revenue half is finally buildable.

Recommendation

What to pursue, in order

Ordered by what unblocks the most downstream work per hour spent. The first three are the critical path to a single live club; nothing else in the portfolio matters as much until they clear.

1

Put trial classes on the Ridge Hill schedule

The control club has an empty calendar — everything downstream waits on this

Four age-band trial classes were created at Ridge Hill on 20–21 May, but the schedule has no upcoming occurrences, so the calendar honestly renders its empty state. The 5 August audit found 7 occurrences in its thirty-day window — thin, and the booking window only opens seven days before class and closes 48 hours before, so most of those are not bookable.

Until a parent can pick a real Ridge Hill trial time, the one clean end-to-end family run that unlocks every other club cannot be performed. This is club-staff work measured in minutes, and it is the highest-leverage unspent hour in the entire engagement.

Needs: Ridge Hill staff · schedule occurrences
2

Build and approve the staff-notification workflow

Without it, a booking request reaches nobody

All Cedarwind HubSpot workflows are off by design and must be rebuilt on Deals — the earlier Contact-based shells are superseded, so this is a build, not a toggle. Staff notification comes first, because until it exists no email carries the signed confirm and deny links, and a request would simply sit unseen.

The specs are written. Cedarwind builds; Ibtissam reviews copy and approves the message map, then names a staff owner and backup per club. The remaining branches — confirmation, denial, reminder, account nudge — get built and tested behind it.

Needs: Cedarwind builds Ibtissam approves copy + names owners
3

Turn the machinery on once, globally — then prove it at Ridge Hill

Three ops steps, then the run that converts evidence into a live club

Provision the production Redis lock and prove it with a two-instance concurrency test; apply and verify the HubSpot Deal schema with the guarded additive-only script; put a real edge rate limit in front of signup, since the in-app throttle is best-effort only.

Then one clean end-to-end family at Ridge Hill: exactly one parent and one child created, exactly one valid Mindbody email, staff one-click confirm, verified enrolment, family linked to the original child record, every message sent once. That test log — signed by Ibtissam and the club manager — is what flips Ridge Hill’s evidence flags. Watch the first five families with the per-club kill switch in reach.

Needs: Cedarwind · ops + run Ibtissam + club manager · sign the log
4

Repeat per club, six times

Now genuinely unblocked — roughly 1–2 hours of club setup each

Every expansion club already has API access and a dedicated trial calendar. What each still needs is its own verified $0 Service with confirmed price and applicability, write acceptance for its gender and relationship catalogs, a routing test, and its own end-to-end family run. Cedarwind re-runs the read-only audit after each club’s setup and records that club’s observed IDs — nothing copied from Ridge Hill.

Sequence by inventory: FiDi, Fishtown and LIC have the fullest calendars. Do Allston last — it additionally needs a HubSpot pipeline, a staff owner, a published address, and an emergency-contact field the form does not yet collect. When the first clubs are live, point court16.com/request-free-trial at the new page and retire the legacy form and its workflows together.

Needs: Club staff · Service + schedule Cedarwind · audit, routing, E2E per club
5

Land the August work on main

A correctness problem disguised as housekeeping

Fifty-two commits, 158 files and the entire current safety architecture sit on agent/family-account-handoff. Anyone reading main — a new engineer, an auditor, a future vendor — sees a six-week-old system and the superseded belief that the write-mode flag protects production. The archived April status file has already been given a caution banner on the branch; that fix does not exist on main.

Merge it. Cheap, and it removes a real chance of somebody acting on stale safety assumptions.

Needs: Cedarwind · one merge
6

Start the attribution clock

Hours of clicks, no code — and the cost of waiting is permanent

Confirm or create GA4, deploy the HubSpot and GA4 tags on the booking subdomain, add a self-referral exclusion, and remove the dead Universal Analytics tag that has collected nothing since 2023. That is the whole of phase zero.

It earns a slot above the bigger measurement build for one reason: the GA4 export to BigQuery is not retroactive. History only accrues from the day it is switched on. It also lights up HubSpot source attribution that is already coded and dormant — the booking form reads and forwards the HubSpot visitor cookie today, but that cookie is never set on the booking subdomain, so the field arrives empty.

Needs: Anthony · GA4 access Cedarwind · hours
7

Make the money visible, then connect spend

The prerequisite quietly cleared in July

Two to three weeks. The only genuinely new engineering is the Mindbody read side — sales, visits and contracts per club — and the authentication, token caching and pagination already exist. Output is dollars per club: new members, new-member revenue, recurring revenue, trial-to-member rate, blended acquisition cost and marketing efficiency ratio. Deliberately no data warehouse: two tables and a few tens of thousands of rows, so Postgres and SQL views answer it for essentially nothing.

Then spend — manual and CSV entry first, since it ships in a week with no integrations and is the permanent home for print, event and signage spend no ad API will ever see. Then the ROI view in the campaign console, where the existing double-down / investigate / cut engine finally has dollars behind it. Apply for the Google developer token now regardless — the 5-to-14-day approval is the long pole.

Needs: Anthony · Google Ads access + who runs the ads a UTM convention everyone follows

One standing decision, alongside all of the above

The court16-booking-ideal fork removes the manual staff-confirm click entirely — the parent creates their Mindbody account inside the wizard through OAuth, the booking confirms immediately, and staff get an FYI with an escape-hatch deny link. It has a clean end-to-end smoke behind it and has sat untouched since 25 May.

Production went the other way: Option 1, recorded on 17 July, has Mindbody own every password and account-link email while HubSpot only reminds, and family completion is staff-verified on the original child record. That was a deliberate call driven by a real constraint — Mindbody’s public API exposes no account-claim flag, so family completion genuinely cannot be proven programmatically.

The fork is therefore not a drop-in upgrade, and it should stop being carried as if it might be. Either fold its OAuth account-creation step into the current flow as an enhancement, or formally retire it. Leaving it as an undecided parallel branch is the one outcome with no upside.

The realistic advanced step is a geo-holdout test — seven clubs are natural test cells, a cleaner read on causality than any attribution model.
